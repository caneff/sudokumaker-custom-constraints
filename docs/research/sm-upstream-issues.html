SudokuMaker Fix List

Each one comes from a live probe, a timed run, or a read of the solver bundle's function body. Silent wrong answers

7 issues

The app shows no error. A helper returns the wrong cells, a rule stops enforcing, or the same puzzle solves two ways. These matter most because nobody notices.

SM-01correctness

The low/high digit-group check builds both masks from the low half

What happens
The function that recognises a two-group digit list as “polarity (low/high)” (labelled groupsArePolarityPair) builds its high mask with the same digit < midpoint test as its low mask. Both masks are the low half, so it only asks whether the low group is one of the two groups.
Repro
On a 1–9 spec: [{1,2,3,4}, {6,7,8,9}] → true, as expected. [{1,2,3,4}, {5}] → true. [{1,2,3,4}, {1,2,3,4}] → true. [{6,7,8,9}, {1}] → false. Present in the minified bundle as served.
Fix
Use digit > midpoint (or >=, per the intended split) for the high mask.
Where
Next to the parity-pair, modular-class and entropy-set checks used to describe digit groups.
SM-02correctness

getCellsTouchingEdge returns a wrong cell id on a border edge

What happens
helpers.geometry.getCellsTouchingEdge(edgeId) converts coordinates with the unchecked getIdFromCoords. For an edge on the board's border, one of the two coordinates is off the grid, and the unchecked formula x + y * width turns it into a real, in-range id of an unrelated cell instead of undefined.
Repro
The same formula gives {x: -1, y: 3} → the last cell of row 2. A left-border edge therefore “touches” a cell on the far right of the row above.
Fix
Use getIdFromCoordsSafe and drop undefined.
Where
helpers.geometry.getCellsTouchingEdge; helpers.cellIds.getIdFromCoords vs getIdFromCoordsSafe
SM-03correctness

replaceComponent with a custom component does nothing

What happens
puzzle.replaceComponent(instance, new X(...)) works when X is a built-in such as SkyscraperComponent. When X is a custom component from a sibling code segment, the swap produces nothing and the rule never enforces. No error appears in the UI or the console.
Why it bites
The app's own edge-clue template uses exactly this shape: a watcher waits for the clue cell's value, then swaps itself for the real component. Copying the template with a custom target silently disables the whole constraint.
Fix
Support custom targets, or throw a visible error when the replacement is not a built-in.
Where
The component-swap handling for ReplaceComponent changes; built-in targets swap in, custom-class targets do not.
SM-04correctness

A custom validate that returns { valid: false } counts as a pass

What happens
The custom-code wrapper tests the author's return value for truthiness: validateWrapper() ? VALID : { valid: false, message: `unable to satisfy ${this.name}` }. An object is truthy. So the result shape the built-in components return is read as satisfied, every time, in the solver and in the editor.
Repro
One custom component on r1c2 that requires a 4. Type 5 into r1c2. With return false, the cell turns red. With return { valid: false, message }, it stays black.
Fix
Accept the object form (read .valid when the return is an object), or log an error for any non-boolean return.
SM-05soundness

Every search branch shares the same component objects

What happens
Cloning the solver state copies each cell's value and candidates but copies the component set by reference. Candidate state is thrown away on backtrack; anything a component stored on instance is not. A flag computed from one branch's candidates stays set in a parent state where it is false, and the component then removes a true candidate.
Second form
A memo written on the path that called puzzle.stop() outlives the branch the stop killed. The next visit to that state matches the memo, returns early, and never stops again, so the dead branch is searched.
Fix
Say so in the custom-constraint documentation. Better: give components a per-state scratch slot that is cloned with the state.
Where
The solver state's copy constructor: constraintComponents = new Set(other.constraintComponents); the per-cell component map clones its Sets but not their members.
SM-06correctness

getCoordsPointedAtByOuterClue swaps the two bottom corners

What happens
In the straight-ray branch, BottomRight yields {x: i, y: height-1-i}, which starts at the bottom-left cell. BottomLeft yields {x: width-1-i, y: height-1-i}, which starts at the bottom-right. TopLeft and TopRight are correct. All four corner cases also run min(width, height) steps, which is not the corner-to-corner diagonal on a non-square grid.
Repro
On a 9x9, the bottom-right outer clue's ray starts at (0,8); the bottom-left ray starts at (8,8).
Fix
Swap the two bottom cases.
Where
helpers.geometry.getCoordsPointedAtByOuterClue(outerCellId) with diagonalType omitted
SM-07correctness

SelfCounting uses a different engine when verbose solving is on

What happens
SelfCountingComponent.initialize emits a sum-based engine when verbose solving is enabled and a state-based engine otherwise. The two prune differently, so the same puzzle can step, time and rate differently depending on whether explanations are being produced.
Fix
Use one engine and gate only the explanation text on the flag.
Where
SelfCountingComponent.initialize, alongside its per-digit MaxDigitCountComponents

Solver speed & strength

3 issues

Answers are right, but the solver is slower or weaker than it needs to be.

SM-08speed

Cell ids from the geometry helpers slow the solver until coerced with | 0

What happens
Ids from puzzle.getCellAt, helpers.geometry.getAllRows() and getAllColumns() look like plain integers: typeof is "number" and they compare === to ids from the puzzle JSON. The solver still runs slower when a component is built on them. A likely cause is the JS engine treating them as doubles rather than small integers.
Measured
A 9x9 board with eighteen HouseComponents for rows and columns, built straight from getAllRows()/getAllColumns(): 1.18× the time of the same houses as cages. The identical code with .map(c => c | 0): 0.97×. Ids derived through getCellAt cost about 1.3× per candidate read. Four interleaved rounds, cold, non-deterministic solve off.
Fix
Coerce ids to small integers inside the helpers. The two line helpers are also one-shot generators, not arrays, which the documentation does not say.
SM-09strength · speed

Built-in sum propagation is weaker than a standard cage propagator

What happens
Compared with the sum handler in Interactive Sudoku Solver (sigh/Interactive-Sudoku-Solver), SudokuMaker's sum components have no required-digit reasoning; no cage/house complement; a multi-target cage relaxed to the whole [min, max] interval, so a sum between the allowed targets is admitted; bounds only for repeat-allowed and weighted sums. The bounds pass rescans every other cell for each cell, O(n²) per cage, and allocates a fresh Set per call. In a no-repeat cage, whether a placed digit is excluded from the remaining combinations depends on the order of cellIds.
Also
WeightedSumComponent accepts positive whole weights only, so a difference or a negative coefficient needs a custom component.
Fix
Precompute per-cage combination masks and filter by required digits and the actual allowed sums rather than the interval.
SM-10speed

“Which cells see each other” is an unindexed walk

What happens
getCellsCanHaveRepeats makes O(n) calls to getCellsSeenByCell, and each call walks every component on that cell. A component that needs peer information calls these from update, which runs thousands of times per solve.
Fix
Build a peer bitmask per cell once after all constraints are registered, and expose it read-only.

Authoring API

6 issues

Nothing breaks at runtime, but each of these sends a constraint author the wrong way first. Most need a sentence of documentation or a thrown error.

SM-11api

A component cannot tell a trial placement from the real board

What happens
AutoStep places digits hypothetically, propagates, and removes the digit when the branch dies. Custom update runs inside those trials and gets no signal that it is in one. Most of what it observes is a branch, and its last observation is often a branch being torn down.
Measured
A logging component on a uniquely solvable 9x9 variant recorded 55,537 house snapshots; 25,832 held states impossible for the solution. A plain sudoku with no custom rule shows the same, 1,393 of 3,274. Anyone debugging a rule by logging from update reads branch states as board states.
Fix
Document the call context. A read such as puzzle.isHypothetical would let diagnostics filter.
SM-12api

Main code and components get two different helpers objects

What happens
Main code receives the extended helpers. Inside a component, helpers.lines and helpers.misc are undefined and helpers.geometry.getSubsetsPerRegion does not exist. Nothing in the documentation mentions the split; an author finds it only when the call fails at solve time.
Fix
Expose the same read-only helpers in both, or document the split beside the helper list.
SM-13api

An exception in validate reads as “unable to satisfy <name>”

What happens
A throw inside a custom validate is caught, logged to the console, and treated as false. The verdict then reads “This puzzle is broken: unable to satisfy <name>”, the same text as a genuine rule violation. A typo looks like a broken puzzle.
Fix
Show the exception text in the verdict, or label it as a code error.
SM-14api

Custom components cannot set a value; built-ins can

What happens
The puzzle view handed to update has no way to build a SetValue change. Built-ins such as SameGroupComponent yield one directly from onValueSet. A custom component must remove candidates down to one instead, which is more changes and more code.
Fix
Add a setValueChange(value, cell) builder to the solver-time puzzle.
SM-15api

DigitSet set operations change the set they are called on

What happens
a.intersect(b), union, subtract and xor modify a and return it. The chaining shape reads as pure. puzzle.getCandidates returns a DigitSet, so intersecting it in place is an easy mistake.
Fix
Document it on the type, or add non-mutating variants.
SM-16api

A local const silently hides an injected global

What happens
Custom code is compiled as new Function(...Object.keys(globals), code), so the injected utilities (SudokuDigitSet, DigitSet, MathUtils, ArrayUtils, SetUtils, …) are plain parameters. A top-level const with one of those generic names is legal and shadows the utility with no warning.
Fix
Namespace the injected utilities, or warn at load time when a segment redeclares one.

Editor

2 issues

What a setter or solver sees on screen.

SM-17ux

No keyboard entry past 9, and the wide pad swallows keys

What happens
The app supports digits above 9 but has no hotkey for them; they need the on-screen pad. While the pad's second screen (10–12) is showing, keys 1–9 do nothing at all.
Repro
A 9x9 custom puzzle with digits 1–12. Open the wide pad, page to the second screen, press 2 on the keyboard with a cell selected: nothing is entered.
Fix
Keep 1–9 hotkeys live on every pad screen, and accept a multi-key or modifier entry for 10 and up.
SM-18ux

A conflict paints the whole component red

What happens
The conflict highlight marks every cell in the component's cellIds. No cell list on a validate result is read, for built-ins either. One wrong digit on a long custom line turns the whole line red. A disabled or solver-ignored constraint also loses its highlighting, with nothing on screen to say so.
Fix
Read an optional cells field from the validate result and highlight only those.
Where
The puzzle-queries worker's validateGrid, which collects invalidCells per component
